Design Decisions and Conventions</strong></h1><h2><strong>1.1 Multi-Tenancy: Schema-per-Tenant</strong></h2><p>Each onboarded organisation gets a dedicated PostgreSQL schema (e.g. tenant_acme, tenant_globex). A global schema holds only the tenants registry table. Application middleware resolves the correct schema from the tenant's slug at request time by issuing SET search_path = &lt;schema_name&gt; at the start of each database connection/transaction. This approach provides strong logical isolation, simple per-tenant backup/restore, and avoids row-level tenant_id filtering on every query.</p><h2><strong>1.2 UUID Primary Keys</strong></h2><p>All tables use gen_random_uuid() as their default primary key. This prevents enumeration attacks on public-facing IDs, supports distributed inserts without collision, and simplifies future data migration or merging across tenants.</p><h2><strong>1.3 Soft Delete</strong></h2><p>All business entities include a deleted_at TIMESTAMPTZ column (default NULL). Deletion is performed by setting deleted_at = NOW(). All indexes on soft-deletable tables use WHERE deleted_at IS NULL partial indexes for performance. Application queries must always include WHERE deleted_at IS NULL unless explicitly querying deleted records (Admin only).</p><h2><strong>1.4 Timestamps</strong></h2><p>All mutable tables carry created_at and updated_at as TIMESTAMPTZ NOT NULL. The audit_trail_logs table is append-only and has only created_at — no updated_at or deleted_at, enforced by PostgreSQL RULEs.</p><h2><strong>1.5 Immutable Audit Trail</strong></h2><p>audit_trail_logs uses PostgreSQL RULEs to block all UPDATE and DELETE operations at the database layer, independent of application-layer controls. Every state transition, user action, and system event is recorded here with a JSONB payload capturing relevant before/after state.</p><h2><strong>1.6 Polymorphic File Store</strong></h2><p>uploaded_files uses a polymorphic pattern (entity_type + entity_id) to associate files with any entity type across the schema without creating separate file junction tables for each entity. Acceptable MIME types and the 10 MB file size limit are enforced at both application and database layers.</p><h2><strong>1.7 AI Model Security</strong></h2><p>The api_key_enc column in ai_models stores the API key encrypted with AES-256 using an application-managed encryption key (stored in environment variables, never in the database). The api_key_enc value is never returned in any API response after initial registration.</p><h1><strong>2. Entity Relationship Narrative</strong></h1><p>The following describes the key relationships between entities in the per-tenant schema:</p><h2><strong>4.1 User Hierarchy and Mappings</strong></h2><p>users is the central entity for all personas. Admin creates all users. manager_auditor_mappings and manager_client_mappings create many-to-many bridges between managers and their teams/clients. client_business_units hang off each client user and represent the organisational units that can be included in audits.</p><h2><strong>4.2 Audit Ownership Chain</strong></h2><p>An audit belongs to one manager and one client. audit_business_units creates a scoped subset of the client's BUs for a particular audit engagement. This is the anchor for all scope line items and auditor assignments within that audit.</p><h2><strong>4.3 Scope and Assignment</strong></h2><p>audit_scope_line_items hang off audit_business_units. auditor_audit_assignments map an auditor to a BU within an audit. auditor_line_item_assignments optionally narrow this to specific items. line_item_responses stores the auditor's answer — one row per auditor per line item (unique constraint ensures no duplicate submissions).</p><h2><strong>4.4 Exception Flow</strong></h2><p>exception_requests FK to audit_scope_line_items and carry a status lifecycle (pending → approved/rejected). On approval, the application updates audit_scope_line_items.status to exception_approved. uploaded_files with entity_type=exception_evidence are linked to the exception_requests.id via entity_id.</p><h2><strong>4.5 Report Chain</strong></h2><p>audit_reports FK to audits. Each re-generation creates a new version row. The DOCX file is stored in uploaded_files with entity_type=audit_report and the file_id FK links back. client_report_feedback rows FK to audit_reports, with one row per section comment.</p><h2><strong>4.6 Polymorphic Files</strong></h2><p>uploaded_files uses entity_type + entity_id to associate files with any parent entity. Application code must validate that the supplied entity_id exists in the correct table for the given entity_type before inserting.</p><h1><strong>5.
